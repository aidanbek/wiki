# Redis Streams

Тип данных в Redis — append-only лог записей с уникальными id (по времени). Даёт persistent-лог с consumer groups внутри
того же Redis, без отдельного брокера. Зрелее, чем старый паттерн «очередь на списках/pub-sub».

## Возможности

- `XADD` добавляет запись, `XRANGE`/`XREAD` читают; id монотонно растут (`<ms>-<seq>`).
- **Consumer groups** (`XREADGROUP`): несколько воркеров делят поток, каждый ack'ает (`XACK`) обработанное.
- **PEL** (Pending Entries List) хранит выданные, но не подтверждённые записи; `XAUTOCLAIM` переназначает зависшие
  (основа для ретраев и [DLQ](../../async-processing/patterns/dead-letter-queue/index.md)).
- Ограничение размера (`MAXLEN`/`MINID`) для усечения лога.

## Когда выбирать

- Уже используете Redis и нужен лёгкий persistent-стрим с consumer groups без поднятия Kafka/RabbitMQ.
- Умеренные объёмы, низкая задержка, простые сценарии очереди событий.

## Подводные камни

- Durability ограничена политикой Redis (RDB/AOF) и репликацией — это не замена Kafka по гарантиям и масштабу.
- Память — главный лимит: лог живёт в RAM, нужно усекать (`MAXLEN`), иначе рост без границ.
- Нет богатой маршрутизации и партиционирования уровня Kafka; реплеи ограничены retention.
