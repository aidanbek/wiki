# Idempotency Keys

Механизм, позволяющий безопасно повторять небезопасные запросы (POST). Клиент присылает уникальный ключ в заголовке (напр.
`Idempotency-Key`), сервер запоминает результат первой обработки и на повтор с тем же ключом возвращает тот же ответ, не
выполняя операцию дважды.

## Зачем

- Сеть ненадёжна: клиент не знает, дошёл ли запрос, и ретраит. Без идемпотентности — двойное списание, дубль заказа.
- GET/PUT/DELETE идемпотентны по семантике HTTP; проблема именно с POST (создание, платежи).

## Как реализовать

- Клиент генерирует ключ (UUID) на бизнес-операцию и переиспользует его на ретраях.
- Сервер атомарно сохраняет `(key → ответ/статус)`; обработка и запись результата — в одной транзакции.
- Повтор: завершённый ключ → отдать сохранённый ответ; ключ «в процессе» → 409/подождать (защита от гонок).
- Ключам ставят TTL (напр. 24 ч).

## Подводные камни

- Один и тот же ключ с **другим телом** запроса — отвергать (часто проверяют хэш payload), иначе ключ «переиспользуют».
- Гонка двух одновременных запросов с одним ключом — нужен лок/уникальный индекс на ключ.
- Идемпотентность ≠ дедупликация навсегда: TTL и разумные границы операции.
