SOLID

Пять принципов ООП Роберта Мартина — фундамент гибкой архитектуры, защита кода от «гниения».

## Принципы

- **SRP** (Single Responsibility) — один класс, одна причина для изменения.
- **OCP** (Open/Closed) — открыт для расширения, закрыт для модификации.
- **LSP** (Liskov Substitution) — подтипы взаимозаменяемы с базовым типом.
- **ISP** (Interface Segregation) — много узких интерфейсов лучше одного широкого.
- **DIP** (Dependency Inversion) — зависимость от абстракций, не от конкретики.

## Различия между схожими принципами

### SRP vs ISP (оба про «разделение»)

SRP — о классе/модуле: одна причина для изменения, одна роль. ISP — об интерфейсе: клиент видит только нужные ему
методы. `User` может иметь одну ответственность (SRP), но выставлять разные интерфейсы для разных клиентов (ISP):
`IAuthenticatable` для login, `IProfileEditable` для UI. Нарушение SRP даёт God Object, нарушение ISP — Fat Interface.

### OCP vs DIP (оба про абстракции)

OCP — цель: расширение без модификации через полиморфизм. DIP — механизм: зависимость от абстракций, инверсия
направления зависимостей. DIP — инструмент для OCP, но не единственный (есть плагины, events). OCP говорит «что»
(расширяемость), DIP — «как» (через интерфейсы).

### LSP vs полиморфизм в OCP

OCP разрешает добавлять новые подтипы для расширения. LSP ограничивает, какие подтипы допустимы — они должны соблюдать
контракт базового типа. OCP про возможность расширения, LSP про его корректность. Пример нарушения: `ReadOnlyList`
наследует `List`, но бросает исключение в `Add()`.

### SRP vs High Cohesion (GRASP)

High Cohesion — методы класса тесно связаны и работают над общей концепцией (техническая мера). SRP — у класса одна
причина меняться, один стейкхолдер (организационная мера). Класс может быть cohesive, но нарушать SRP. SRP строже и
чётче, High Cohesion — более расплывчатая метрика.

### ISP vs DIP

ISP — про размер и содержимое интерфейса (разделяй толстые). DIP — про направление зависимости (инвертируй к
абстракции). Можно соблюдать DIP с толстыми интерфейсами (нарушая ISP) и наоборот — иметь узкие интерфейсы, но зависеть
от конкретных классов.

### OCP vs YAGNI (конфликт)

OCP требует точек расширения через абстракции, YAGNI запрещает функциональность «на будущее». Разрешение: применяй OCP
только к точкам изменчивости, которые реально происходят (Protected Variations из GRASP). Добавляй абстракцию при втором
случае изменения, не при первом — OCP реактивный, не проактивный.
