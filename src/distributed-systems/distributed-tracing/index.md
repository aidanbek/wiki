Distributed Tracing

Способ проследить путь одного запроса через десятки микросервисов. Без трейсинга в распределённой системе почти
невозможно понять, где именно теряются миллисекунды и какой сервис стал узким местом.

## Модель данных

- **Trace** — весь путь запроса целиком, с уникальным trace id.
- **Span** — одна операция внутри trace (HTTP-вызов, запрос в БД), со своим временем начала/конца и метаданными.
- Span'ы образуют дерево через parent/child — видно, что и за чем вызывалось.

## Как это работает

- На входе генерируется trace id; контекст (trace id + span id) передаётся дальше через заголовки (W3C Trace Context).
- Каждый сервис создаёт свои span'ы, и **propagation** контекста связывает их в один trace.
- Span'ы экспортируются в бэкенд, который собирает из них полную картину.
- Чтобы не утонуть в объёме, применяют **sampling** (head- или tail-based).

## Инструменты

- [[opentelmetry]] — вендор-нейтральный стандарт и SDK для инструментирования (API + экспортёры).
- [[jaeger]] и [[zipkin]] — бэкенды для сбора, хранения и визуализации трейсов.
- Связка обычная: OpenTelemetry собирает данные, Jaeger/Zipkin их показывают.
