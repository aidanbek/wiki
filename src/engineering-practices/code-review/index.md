# Code Review

Проверка изменений другим инженером перед слиянием. Цель не «найти виноватого», а повысить качество, распространить знания
и поймать проблемы дёшево — до прода.

## Что проверять

- Корректность и крайние случаи; соответствие требованиям.
- Читаемость и соответствие конвенциям проекта (код читается чаще, чем пишется).
- Тесты на новое поведение; безопасность и обработка ошибок.
- Не выискивать стиль вручную — это работа линтеров/форматтеров в [CI](../../tools-and-setup/ci-cd/index.md).

## Практики

- **Маленькие PR** — ревью большого диффа поверхностно; дробить изменения.
- Быстрый отклик: затянутое ревью блокирует команду.
- Комментарии о коде, а не о человеке; различать «надо исправить» и «можно подумать» (nit).
- Автор описывает контекст и причину изменения в PR.

## Подводные камни

- **Rubber-stamping** (LGTM не глядя) — ревью для галочки бесполезно.
- Бесконечный бикешеддинг по мелочам вместо сути; спорные правила — в линтер, а не в спор на каждом PR.
- Слишком большие PR неизбежно ревьюят плохо — это проблема процесса, а не ревьюера.
