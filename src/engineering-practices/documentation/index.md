# Documentation

Знание, вынесенное из голов в текст, чтобы команда не зависела от одного человека. Хорошая документация отвечает на
вопросы «почему так», которые не виден из кода.

## Виды

- **README** — что это, как запустить, как внести вклад.
- **Reference** — API/конфиги; в идеале генерируется из кода/схемы ([OpenAPI](../../web-development/api-design/documentation/index.md)).
- **How-to / tutorials** — пошаговые сценарии.
- **Explanation / ADR** — обоснование решений (см. [ADR](../../operational-excellence/architecture-decisions/index.md)).
- **Runbooks** — что делать при инциденте (см. [runbooks](../../operational-excellence/incident-management/runbooks/index.md)).

## Принципы

- Документируй **«почему»**, а не «что» — «что» видно из кода и быстро устаревает в тексте.
- Держи доку рядом с кодом (docs-as-code, в репозитории) — тогда она ревьюится и обновляется вместе с изменениями.
- Учитывай аудиторию: новичок, дежурный, потребитель API — разные документы.

## Подводные камни

- **Устаревшая документация хуже отсутствующей** — она вводит в заблуждение; что нельзя поддерживать, лучше автоматизировать
  или удалить.
- Дублирование одного факта в нескольких местах гарантирует рассинхрон — один источник правды.
