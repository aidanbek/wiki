# Rate Limiter

Сервис, ограничивающий число запросов от клиента за интервал. Задача — точно считать лимиты в распределённой среде с
несколькими инстансами и минимальной задержкой. Алгоритмы разобраны в
[rate limiting](../../../infrastructure/resilience/rate-limiting/index.md) — здесь акцент на распределённый дизайн.

## Где считать

- **Token / leaky bucket** — сглаживают всплески, хранят немного состояния на ключ.
- **Sliding window** — точнее на границах окна, но дороже по памяти.
- Состояние (счётчики) — в общем сторе с низкой задержкой, чаще всего Redis.

## Распределённый аспект

- Несколько инстансов API должны видеть общий счётчик → централизованный Redis с атомарными операциями (INCR+EXPIRE или
  Lua-скрипт для атомарности проверки и инкремента).
- Альтернатива для огромного масштаба — локальные лимиты на инстанс с периодической синхронизацией (быстрее, но менее
  точно).

## Trade-off'ы

- Точность vs задержка/стоимость: централизованный счётчик точен, но добавляет сетевой hop и становится горячей точкой.
- Поведение при недоступности стора: **fail-open** (пропускать) безопаснее для UX, **fail-closed** — для защиты.
- Возвращать `429` с заголовками `Retry-After`/`X-RateLimit-*`, чтобы клиент мог корректно отступить.
- Гонки на инкременте лечатся атомарными операциями, а не «прочитал-увеличил-записал».
