# SSRF (Server-Side Request Forgery)

Атакующий заставляет сервер сделать HTTP-запрос по адресу, который выбирает атакующий. Опасность в том, что запрос идёт
изнутри периметра — туда, куда снаружи доступа нет: внутренние сервисы, админки, облачные метаданные.

## Типичный вектор

- Функция, которая по URL от пользователя что-то скачивает: webhook, импорт по ссылке, превью, прокси изображений.
- Классическая цель в облаке — endpoint метаданных `169.254.169.254`, откуда можно вытащить временные креды роли (IMDSv1).

## Защита

- **Allowlist** разрешённых хостов/схем вместо blacklist; запрещать `file://`, `gopher://`, редиректы на приватные сети.
- Резолвить DNS и проверять итоговый IP против приватных диапазонов (10/8, 172.16/12, 192.168/16, 127/8, link-local) —
  с защитой от **DNS rebinding** (повторная проверка после резолва).
- Запросы наружу — через egress-proxy с правилами; в облаке включить IMDSv2 (требует токен).
- Не возвращать клиенту тело ответа и детальные ошибки (борьба с blind SSRF).

## Подводные камни

- Редиректы и нестандартные представления IP (десятичный, IPv6-mapped) обходят наивные проверки.
- SSRF часто — лишь первый шаг к доступу во внутреннюю сеть; глубокая защита по слоям критична.
