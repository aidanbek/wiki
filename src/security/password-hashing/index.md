# Password Hashing

Пароли хранят не в открытом виде и не под обычным хэшем, а под **медленной** хэш-функцией с солью. Цель — чтобы при утечке
БД перебор паролей был экономически невыгоден.

## Почему не SHA-256

- Быстрые хэши (MD5, SHA-*) рассчитаны на скорость — GPU перебирает миллиарды в секунду; идеально для атакующего.
- Нужны **password hashing functions**, специально сделанные медленными и настраиваемыми по «стоимости».

## Алгоритмы (предпочтения)

- **Argon2id** — современный выбор по умолчанию; настраивается память + время + параллелизм, устойчив к GPU/ASIC.
- **scrypt** — memory-hard альтернатива.
- **bcrypt** — проверенный временем, но ограничен ~72 байтами ввода и без memory-hardness.
- **PBKDF2** — когда нужен FIPS-совместимый вариант.

## Обязательные практики

- **Соль** — уникальная случайная на каждый пароль (от радужных таблиц); хранится рядом с хэшем.
- **Pepper** — секрет вне БД (в HSM/конфиге), добавляется к паролю; защищает при утечке только БД.
- Сравнение хэшей — в постоянном времени; cost-параметры повышать со временем и при логине миграционно перехэшировать.

## Подводные камни

- Не «шифровать» пароли (шифрование обратимо) — только односторонний хэш.
- Слишком высокий cost → логин тормозит и сам становится вектором DoS; подбирать под целевую задержку (~100–250 мс).
